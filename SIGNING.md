# Shelby+ release signing and updates

Earlier releases used an automatically generated, discarded signing key on every CI run. Android identifies an update by **applicationId + signing certificate**, with a nondecreasing versionCode. A new temporary certificate could not update the previous installation; uninstalling removed its private pairing/settings data. An Actions artifact or ordinary SHA256SUMS file does not restore a lost private key.

The hardened release workflow has **no temporary-key fallback**. No release is ready until its permanent key is configured, the expected public fingerprint matches the key and built app/add-on, and all validation passes. `dev.tvremote.setup` and `dev.tvremote.setup.keys` stay stable. Versions use the existing formula `100000 + major*10000 + minor*100 + patch`; each component must stay below 100 and each published release must strictly increase versionCode.

## Administrator setup (private key stays private)

1. Create a GitHub Actions **environment named `shelby-release`**, restrict deployments to reviewed release tags and the reviewed branch used for the non-publishing readiness check, require reviewers, and protect the workflow files/tags against unauthorized edits. Do not grant signing secrets to pull-request or general test jobs.
2. On a trusted offline/administrator machine, generate a permanent RSA key once, or reuse a securely backed-up existing permanent key. For a new key, run `keytool -genkeypair -storetype JKS -keystore "$HOME/shelby-release.jks" -alias shelby-release -keyalg RSA -keysize 3072 -validity 10000`. Enter strong passwords interactively; do not put passwords in commands, shell history, git or screenshots. Back up the encrypted keystore and recovery information in separate secure offline locations. JKS base64 is **not encryption**.
3. Add these **environment secrets** through GitHub's encrypted Secrets UI or interactive `gh secret set --env shelby-release`: `SHELBY_TV_KEYSTORE_BASE64`, `SHELBY_STORE_PASSWORD`, `SHELBY_KEY_PASSWORD`, and `SHELBY_KEY_ALIAS`. The first is the single-line base64 encoding of the keystore. Transfer it through a protected temporary file/stdin, never a command argument or log. Store/key passwords may differ. Delete unneeded temporary encodings afterward.
4. Run `keytool -list -v -keystore "$HOME/shelby-release.jks" -alias shelby-release` and enter its password interactively. Record only the **public certificate SHA-256**. Set environment variable `SHELBY_RELEASE_CERT_SHA256` in GitHub Actions **environment Variables** to those 64 hex digits (colons accepted). This public fingerprint is embedded in the APK as its update trust anchor.
5. Run **Shelby+ Remote TV APK → Run workflow → verify_persistent_signing = true** against this reviewed branch. The protected readiness job opens the keystore, checks its public pin, builds the APK, verifies its signatures and the bundled add-on's matching signer, and uploads public certificate evidence only. It never creates a release. If dispatch is not offered while the workflow exists only on a feature branch, first put the reviewed workflow on the default branch; never use an older permissive workflow as a workaround.
6. For the **first** migration from an old temporary-key release, explicitly set environment variable `SHELBY_INITIAL_MIGRATION_APPROVED=true` after reviewing the data-loss warning below. Publishing refuses a changed certificate if the previous release already contains `shelby-update.json`, regardless of that flag. Remove the migration flag after the first permanent release.
7. Only after readiness and all tests pass, push a reviewed `shelby-tv-v<APK version>-<distribution>` tag. The release job again checks the key, built APK, bundled add-on, latest published certificate, versionCode increase and MIT notice. It stages a draft and publishes only after complete assets exist. Keep the permanent key unchanged for all future releases.

The current connector previously returned HTTP 403 for repository Actions secrets and HTTP 404 for the protected environment secrets endpoint (missing environment or inaccessible permissions). This development session cannot claim the protected key is configured merely because workflow code exists. An administrator must complete setup and obtain a successful protected readiness run before publishing. **No release is authorized by the current development task.**

## Local and CI builds

A permanent local build requires `SHELBY_KEYSTORE_PATH`, `SHELBY_STORE_PASSWORD`, `SHELBY_KEY_PASSWORD`, `SHELBY_KEY_ALIAS`, and `SHELBY_RELEASE_CERT_SHA256` in a protected environment. The build script refuses missing configuration; no passwords have source defaults. `app/gradle/shelby-signing.gradle` supplies the same key to the TV app and bundled keys add-on.

General validation CI uses the explicit `SHELBY_TEST_BUILD=1 app/tvsetup/build.sh` mode. It creates a disposable key with random environment-only passwords outside git, signs both APKs, deletes the private key, and produces an artifact labelled **validation only**. Its update pin is empty, so its fork update checker is disabled. This is not persistent-signing readiness and must not be distributed as a release.

## Secure, user-confirmed updates

The native TV app's **Shelby+ Remote → Update now** checks only this fork's latest public GitHub Release. It accepts bounded `shelby-update.json` metadata with a canonical tagged APK URL, stable package, increasing versionCode, checksum, byte length and the embedded permanent certificate pin. Downloads allow HTTPS only, a bounded GitHub-host redirect list, timeouts and a 64 MiB maximum.

After explicit confirmation, the app downloads to its private cache, verifies length/SHA-256, verifies the APK's cryptographic signature with apksig, checks its signer against both the compiled pin and the installed app, and checks package/version against the metadata. Only then does Android's normal full-install session run with user confirmation. Cancelled or rejected downloads are deleted. There is no uninstall, data clear, ADB/silent install, permission/security-setting change or automatic self-update. If Android blocks this installer, use the verified release through the usual external installer instead. Other ecosystem apps retain their existing opted-in upstream update behavior; shared upstream release verification is not weakened or repointed.

Metadata is fetched over system-validated HTTPS; APK authenticity is anchored in the installed/pinned signing certificate, not in an unsigned checksum or arbitrary release notes. A compromised GitHub account without the private key cannot produce an APK accepted by this checker. Release/tag protections and secure offline key backups remain necessary. Certificate rotation/signing lineage is not supported by this initial checker; it fails closed on a changed signer. Real PRISM+ installer behavior still needs hardware testing.

Same-package, same-key Android updates retain the app UID, pairing files, authentication and preferences. Safari must keep using the same TV address/origin to retain its browser cookie. No storage format or pairing API is changed by this work. Do not uninstall or clear app data for a compatible update.

## One-time migration from temporary builds

The private keys for earlier temporary releases were discarded. Their certificates cannot be reproduced or recovered from the APK. The first permanent-key APK therefore **cannot update them in place**, even with a higher versionCode. A fresh installation of the TV app and its matching keys add-on may be necessary, losing local pairings/settings/authentication. Keep the physical remote available; do not uninstall until that loss is accepted. Export only settings supported by the existing app; there is no promise of safely exporting secret pairing material. After migration, keep the permanent key for compatible updates.

## Frontend updates without reinstalling the APK

The current production frontend remains packaged in the signed APK. HTML/manifests are no-store, CSS/JS/icon links include the installed version/update stamp, and the TV page registers no service worker. This safely refreshes the browser after a compatible APK update, but **does not** download new application code independently.

A safe future independent frontend channel would need a separately pinned signing key and signed manifest, hashes for every bundled file, version/ABI compatibility with the installed API, anti-rollback state, strict path/size limits, atomic activation and a packaged rollback copy, plus authenticated owner confirmation. HTTPS/checksums alone are insufficient: remotely supplied JS could use a paired browser's authority to control the TV. Loading arbitrary GitHub Pages/CDN scripts, evaluating release notes, or repointing service workers is not implemented.

iPhone Safari on a LAN HTTP origin generally cannot register a service worker; iOS caches installed icons separately and can discard web storage. Public HTTPS hosting cannot freely control a private HTTP TV because of mixed-content/private-network/CORS restrictions. Such hosting must not weaken pairing, origin/DNS-rebinding checks or expose port 8765 to the internet. No remote-code frontend updater is enabled by this change.
